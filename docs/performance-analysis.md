# 性能测量与优化证据

本文保留历史优化与测量证据，不作为当前性能承诺。当前仅支持桌面浏览器，移动端测试已取消。

## 测试环境与方法

本记录的采样工作站为Linux x64，Intel Core Ultra 7 265K。浏览器Chromium 156.0.8078.4，headless，视口1440×1000、DPR 1。WebGL renderer为ANGLE / Vulkan SwiftShader（软件渲染）；这些数据不代表手机GPU性能。

独立rAF采样保留每一帧原始间隔，未丢弃慢帧。物理与几何时间来自游戏实际执行处；CPU渲染提交耗时不代表GPU执行耗时。基于开发服务运行，包含开发构建开销。真实Android连接检查发现设备列表为空，详见 `device-validation.md`。

## 首轮瓶颈

原始数据：`performance-before.json`。默认各短场景4秒、长场景12秒，不含页面加载和预热时间。

| 场景 | 平均FPS | P95 ms | P99 ms |
|---|---:|---:|---:|
| 默认飞机飞行 | 53.0 | 33.3 | 33.4 |
| 最大翼展飞行 | 58.5 | 16.8 | 33.3 |
| 连续轨道相机 | 40.0 | 33.4 | 50.0 |
| 连续拖翼 | 25.4 | 83.3 | 83.4 |
| 反复进入退出飞行 | 41.3 | 33.4 | 83.3 |
| 反复创建销毁几何 | 25.9 | 83.3 | 83.4 |
| 飞行与重置 | 55.3 | 33.3 | 33.4 |

代码中每次编辑释放全部机体材质再创建，丢失已编译shader，并重复设置画布尺寸。这些工作与实际几何修改没有必要的一一对应。

修复：材质、常量驾驶员几何及机体网格持久复用；每个渲染帧合并更新，只重建变化翼面；移除编辑时无变化的resize和全场景内存遍历；Auto从Low起步。驾驶员的视觉位移直接跟随物理重心，而不是仅移动整个模型。

## 第二轮定位最差帧

原始数据：`performance-intermediate.json`。各短场景6秒，长场景60秒，重置间隔15秒。默认飞行60.0FPS，拖翼57.0FPS，长场景59.7FPS；但长场景存在166.7ms最差帧。

累计原始帧间隔，166.7ms慢帧发生在采样第12549.4ms；首次Medium档采样发生在12550.0ms，shader program数从6增至13。自动升档开启阴影造成实时shader编译尖峰，与该慢帧时间吻合。

修复：Auto档始终不切换阴影，只调整DPR和远景细节；手动Medium/High仍可启用阴影。DPR不变时不重新分配画布尺寸。不通过过滤帧、缩短采样或虚报GPU耗时改善指标。

该轮原始数据由七场景工具写入 [`performance-results.json`（`972e8b2`）](https://github.com/Nigh/glider-3d/blob/972e8b2/docs/performance-results.json)，包含环境、操作次数、帧间隔、资源计数、JS堆信息和异常列表。历史普通手机60FPS目标未完成真机验收；当前不支持移动端，也不以软件渲染桌面结果作手机性能承诺。

一次最终复测在页面完整 `load` 等待阶段超过10秒，尚未进入任何采样场景。工具改为等待 `DOMContentLoaded`，随后仍等待真实“开始设计”按钮与 `window.glider.state === 'design'`，再进行预热和采样；未延长或屏蔽飞行中的慢帧。导航失败不作为性能数据。

## 历史实测（原七场景）

各短场景6秒，长场景60秒，全部场景无未捕获页面异常。原始数据为上方链接的历史版本。以下单位为实际rAF帧间隔，不是模拟步长。

| 场景 | 平均FPS | 平均帧间隔 ms | P95 ms | P99 ms | 最差帧 ms |
|---|---:|---:|---:|---:|---:|
| 默认飞机飞行 | 60.0 | 16.67 | 16.8 | 16.8 | 16.8 |
| 最大翼展24m飞行 | 60.0 | 16.67 | 16.8 | 16.8 | 16.8 |
| 连续轨道相机 | 59.0 | 16.95 | 16.8 | 33.3 | 33.4 |
| 连续拖翼 | 56.5 | 17.70 | 33.3 | 33.4 | 33.4 |
| 反复进入退出飞行 | 58.8 | 17.00 | 16.8 | 33.3 | 33.4 |
| 反复创建销毁几何 | 57.7 | 17.34 | 16.8 | 33.3 | 33.4 |
| 60秒飞行与重置 | 59.9 | 16.69 | 16.8 | 16.8 | 66.5 |

默认飞行采样的物理耗时平均0.044ms、最大0.200ms；CPU渲染提交平均0.328ms。连续拖翼的几何更新采样最大0.400ms，CPU渲染提交平均0.372ms。采样约每250ms进行，不能把“采样最大”当作每次调用的绝对最坏上界。

默认飞行最多79 draw calls、3111三角形；连续拖翼46 draw calls、2947三角形。反复替换几何场景的已上传geometry数保持21、texture数保持1、program数保持6，未在该场景看到资源计数持续增长。60秒场景因画质、远景和水花变化，geometry为22–26、texture保持15、program为6–11；这不等于完整的显存或泄漏证明。

长场景最差帧从中间版本的166.7ms降到66.5ms；仍有孤立慢帧，连续拖翼也未锁定60FPS。真实手机硬件、热降频、Safari、数分钟稳定性与GPU执行时长均未验收。

最终场景实际完成150次相机指针移动、109次翼面拖动事件、15次进入/退出飞行、61次模型替换、60秒场景5次重置。全部场景 `hiddenFrames=0`，结束时页面均为visible；错误列表为空。JS堆增量字段在本环境均为0，不能据此推断没有分配或没有GC。

## Manifold 分区测量方法

本轮对照使用上游 `e451e9d` 与修改前的 PR #61 提交 `972e8b2`，分别在独立开发服务器上串行运行同一份性能工具。每个checkout使用独立Vite预构建缓存，避免共享`node_modules`时互相覆盖。视口固定为1440×1000、DPR 1，浏览器、驱动与实际画质记录在原始结果中。短场景请求3秒，长场景4秒，预热500 ms，重置间隔1秒；完整输入轨迹未完成时，采样持续到完成，并报告实际窗口耗时。

工具现在先点击“开始试飞”并等待模拟时间推进，才采集飞行数据；此前只进入待发射界面的结果不能当作真实积分性能。拖拽使用当前三维顶点手柄，几何生成场景交替修改主翼安装角，不再查找已移除的预设下拉框。

`entryTimesMs` 从进入挑战前计时，到实际积分开始后结束，包含Worker准备、场景构建与启动交互，不等于纯布尔运算时间。风洞稳定气流与连续安装角编辑分开采样。CPU渲染提交耗时不代表GPU执行时长。

每个场景使用独立浏览器context，保留场景前后的原始设计快照。相机轨迹按60次/s、翼端拖动按30次/s、安装角修改按2次/s、进入退出按1次/s生成固定操作数；阻塞后仍完成剩余轨迹。风洞在发送全部目标后等待最后目标实际到达，不把未完成的编辑计为完成。

`compiledGeometry`记录采样前的分区、顶点、三角形数量及最近一次Worker编译请求的计算耗时 `lastCompileMs`；缓存命中也计时，不含模块初始化、消息传输与场景构建。完整场景诊断仅在窗口开始前读取一次，旧版本无此字段时为 `null`。

`longTasks`通过 `PerformanceObserver` 记录窗口内至少50 ms的主线程任务；Worker计算不计入其中，不支持该接口时为 `null`。因此它与编译耗时、模拟推进速度分别报告。

Linux本地运行另在窗口前后通过CDP取得浏览器进程ID，并读取 `/proc` 的PSS/RSS，包含驻留WASM内存。PSS按共享比例计量，RSS求和会重复计算共享页；两者都不是单页或独立显存用量。读取不可用时保存原因，不记为0。

旧版本 `geometryMs` 保留最后一次 `applyAircraft()` 重建耗时，并非当前帧几何耗时；不能将它与新版本的逐帧几何CPU时间直接计算优化倍数。帧间隔仍使用独立rAF时间戳比较，物理耗时读取实际积分遥测。当前短时软件渲染结果不作为硬件帧率承诺。

当前工具的schema 3将FPS定义为实际rAF回调数除以完整输入轨迹窗口耗时，并记录首帧等待与末尾间隙，避免窗口末端的主线程阻塞被平均值漏掉。P95/P99仍只使用实际相邻rAF时间戳；不补造帧或过滤慢帧。

风洞另记录 `simulationProgress`：实际模拟时间增量除以完整墙钟窗口。Worker等待可以保持界面帧率，却延长安装角过渡的墙钟时间，两项必须分开报告。旧版本缺少 `elapsedTime` 诊断，或场景不是风洞时，此项为 `null`。

`physicsMs`为最近完成的积分步CPU耗时，每约250 ms读取一次。Worker等待帧可能重复读到同一步，不能把这些值累加为逐帧CPU用量，也不能将采样P95当作所有积分步的绝对上界。

操作计数的实际持续时间另记为 `interactionElapsedMs`，包含最后一次异步操作的完成等待；不以 `requestedDurationMs` 推算操作吞吐。

浏览器挑战保留默认随机发射扰动，帧间隔对照不等同于逐状态物理对照。确定性物理对照使用 `scripts/contact-performance.mjs`：固定24 m机翼、材料量、滚转角、速度及60 Hz输入，预热一次后测量三次，并检查穿透、断裂归属和能量账本。该脚本可依次接收多个checkout路径，在同一进程中串行比较。

本轮采样参数：

```sh
PERF_SAMPLE_MS=3000 PERF_LONG_MS=4000 PERF_RESET_MS=1000 npm run perf
```

## Manifold 三版本实测

Linux x64、Core Ultra 7 265K、Chromium 156 headless，WebGL由SwiftShader软件渲染，画质Low。三版本使用相同设计、输入轨迹和采样工具；浏览器发射扰动仍随机。原始数据：[上游](performance-upstream.json)、[旧PR](performance-pr61-before.json)、[Manifold](performance-results.json)。

Manifold默认飞机最近一次Worker编译耗时308.7 ms，含29分区、9757顶点及19350三角形；不含Worker初始化、传输和场景构建。风洞连续变角完整发送6个目标并到达最后目标，采样墙钟5.55 s，模拟推进0.767 s，即0.138模拟秒/墙钟秒。

设计拖拽帧率在此场景改善，但普通飞行与稳定风洞的物理耗时高于两份对照，风洞变角与进入场景也更慢。固定60 Hz触地的四组确定性CPU对照及能量、断裂结果见[触地测量](contact-performance.md)。性能回退尚未消除；上述软件渲染帧率不代表硬件GPU表现。
